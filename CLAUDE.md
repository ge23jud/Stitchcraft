# Proc App — Claude Context

## What this project is
"PL Spectrum Stitcher / Converter" — a Windows PyQt5 desktop app for processing photoluminescence (PL) spectroscopy data during Benjamin Haubmann's PhD at TUM. It stitches multi-file power-series spectra into a single spectrum, converts between file formats (.origin / HDF5), visualizes spectra, and runs peak-fitting / threshold-detection analysis.

## Key facts
- **Entry point**: `stitchcraft.py` — builds the `QApplication`, applies the `qt_material` `dark_teal.xml` stylesheet, calls `plotting.apply_pg_theme()`, then shows `StitchApp`.
- **Main window**: `app.py` — `StitchApp(QMainWindow)`, a `QTabWidget` hosting the tabs below.
- **Platform**: Windows-only PyQt5 app (no PySide/Qt6 constraint otherwise).
- **GitHub**: https://github.com/ge23jud/Proc.git
- **Dependencies**: pinned in `requirements.txt` (PyQt5, pyqtgraph, numpy, h5py, scipy, pandas, qt-material, opencv-python, Pillow, matplotlib — matplotlib is only needed because `nw_analysis.py` and `pl.py` import it at module level; see the `plotting/` note below). No `pyproject.toml`/`setup.py`.

## Tabs (`tabs/`)
- **`stitch.py`** — "Stitch / Convert": one tab, two independent converters selected by a "File type" dropdown at the top of the sidebar — adding a third converter later is just another combo entry plus another sidebar page, nothing else needs restructuring.
  - **"PS (.origin) → HDF5"** (the original, pre-2026-08 standalone Stitch/Convert flow): load `.origin` power-series files, preview spectra, pick per-pair overlap "transition spans" (draggable region), dark-spectrum subtraction, power calibration, save as HDF5 or `.origin`.
    - **Added 2026-08 — baseline subtraction**: an optional "Baseline subtraction" group in the sidebar, applied at the very end — after stitching and dark subtraction — sharing the same drag-a-`DraggableSpan`-then-Confirm UX as the TRPL tab's baseline subtraction (own `_ps_baseline_bar` Confirm/Cancel action bar, since the PS page's existing `_ps_nav_bar` is dedicated to pair navigation). "Select baseline range…" computes the current pre-baseline stitched/dark-subtracted result (`_ps_compute_stitch_core()`) and displays it exactly like "Preview result" (`_ps_draw_stitched()`, every power step visible, colored by power) for the user to drag a no-signal window over. **One constant per power step** is then fit — the mean of *that step's own* counts over the picked wavelength range (not averaged across steps) — and, on Confirm, each step's constant is subtracted from just that step's own column (`self._ps_baseline_value` is a `(n_powers,)` array; `_ps_compute_stitch()`, the wrapper every preview/save call now goes through, subtracts it from `counts_diff` via broadcasting after `_ps_compute_stitch_core()`'s own stitching+dark-subtraction+min-shift). Always refits from the pre-baseline data (never the already-subtracted result), so re-selecting after a Reset — or even without one — can't compound an already-applied baseline. Mutually exclusive with transition-span selection (`_ps_mode == "spans"`); changing the loaded input files discards any baseline selection (`_ps_reset_baseline_state()`), since it no longer applies to different data. "Save as HDF5…" additionally writes the fitted constants as a `(n_powers,)` `Baseline` dataset (with the shared fit range as nm in a `FitRange` attribute) via `io_utils._write_h5_file(..., baseline_value=, baseline_range_nm=)`; `SpectraDiff` gets a new `baseline_subtracted` attr alongside its existing `dark_subtracted` one. "Save as .origin…" and "Preview result" pick up the same baseline-subtracted counts automatically (both already went through `_ps_compute_stitch()`) but — since `.origin` has no array-metadata slot — don't record the constants themselves, only the already-subtracted values.
  - **"TRPL (.dat) → HDF5"** (originally the standalone "Convert" tab; merged into this one 2026-08): batch-converts PicoHarp 300 TRPL histogram `.dat` exports to HDF5 (see `io_utils._parse_trpl_dat`). Load one or more `.dat` files, select each in the list and enter the power it was measured at (mW) — power is necessarily per-file since each TRPL scan is one power point, unlike the PS mode's single multi-power-step `.origin` files. Rep. rate (MHz) and spot diameter (µm) are global to the batch and, like the two power-calibration files (atBS/atSample, same format/autosearch idea as PS mode), are **required**, not optional — Pump_fluence and calibrated Power can't be computed without them. "Autosearch" walks each input file's directory *and its parent* (TRPL `.dat` files commonly sit one level below where a sibling `Calibration/` folder lives, e.g. `.../<dataset>/Calibration/` next to `.../<dataset>/TRPL/*.dat`, rather than inside the same folder as PS mode's flat layout) and recurses into any `Calibration/` folder found to handle per-laser subfolders (`Calibration/TiSa`, `Calibration/HeNe`); if that recursion turns up more than one atBS or atSample candidate it's treated as genuinely ambiguous (wrong laser calibration silently applied would be a real correctness bug) and surfaces all candidates in a dialog instead of guessing — the user picks via the per-role "Load…" buttons. "Convert to HDF5" writes one `.h5` per file with a power assigned, next to its source `.dat`, skipping/report­ing files with no power set. Output datasets: `Counts` (raw histogram), `Times` (`0, ns/channel, 2×ns/channel, …`, from the `#ns/channel` header line) with root attr `TimesUnit="ns"`, `Power_uncalibrated`/`Power`/`Pump_fluence` (1-element arrays, mirroring PS mode's dataset+units-attr convention so they stay `_read_h5_spectrum`-compatible), and root attrs `Date` (raw date/time string from the `.dat`'s first header line), `rep_rate_mhz`, `spot_diameter_um`. The atBS/atSample→transmission-factor OLS fit (`P_sample = a · P_BS`) is shared between the two modes via `io_utils._compute_power_transmission()` so both compute it identically.

  Implementation note: the two modes share nothing but the "File type" combo and the canvas/toolbar on the right (a `QStackedWidget` swaps the sidebar page; only one mode is ever visible, so there's no state conflict) — every widget and state variable is namespaced `_ps_*` or `_trpl_*`, i.e. they're really still two independent former-classes' worth of code living in one file. Switching the combo mid-work doesn't discard the other mode's state: leaving PS mode while mid-span-selection tears down the interactive `DraggableSpan` and hides the pair-nav bar but keeps `_ps_mode`/`_ps_pair_idx`/etc., so switching back to "PS" re-arms the selector on the same pair via `_ps_draw_pair()`; leaving/entering TRPL mode just redraws whatever `.dat` file is currently selected in its list (or a welcome message if none).
- **`trpl.py`** — "TRPL" (added 2026-08, unrelated to the "TRPL (.dat) → HDF5" *converter* above other than sharing a file format): load a single TRPL histogram HDF5 file (as written by `stitch.py`'s TRPL-conversion mode, via `io_utils._read_trpl_h5_file`) and fit 1, 2, or 3 exponential decays (a combo box, capped at 3 — not a free-form N) to extract per-component lifetimes. Plots `Counts` vs. `Times` on a log-y axis using the same downsampled/`antialias=False` technique as the TRPL-conversion preview (large histograms, smooth pan/zoom). `Counts = sum_i a_i·exp(-b_i·Times)` components are fit via nonlinear least squares (`scipy.optimize.curve_fit`, bounded to `a_i, b_i > 0`), refit live on every `DraggableSpan` drag-release and overlaid immediately for a live preview; a non-converging fit (`RuntimeError`/`ValueError`) or too few points in the window (`≤ 2` free parameters — every stage, regardless of N, fits exactly 2 free parameters) disables "Confirm" with a status message rather than raising. "Save fit results to HDF5" writes an `analysis` HDF5 subgroup (recreated fresh, same convention as `analysis.py`'s save) with `FitParameters`, `FitCovarianceMatrix`, `FitRange`, `Lifetime` (`1/b_i`), and a descriptive `FitFunction` group attribute (not a live Python callable — HDF5 has no native way to store one); shapes/contents depend on N as described below.
  - **N=1**: exactly the free 2-parameter fit it sounds like — one dragged range (seeded over the full time axis), `a·exp(-b·Times)` fit jointly. `FitParameters`/`FitCovarianceMatrix` are `(1,2)`/`(2,2)`.
  - **N ≥ 2, changed 2026-08 (N=2 first, then generalized to N=3) to an N-stage *iterative* fit**, never one joint 2N-parameter optimization: PL decays here are typically ordered slow/medium/fast, where at long enough times faster components have already died out and only the slower ones remain. Stage 0 drags a **tail** range (defaulted to the last 20% of the time axis for stage 0, widening progressively for later non-final stages via `_default_stage_bounds()` — e.g. N=3's stage 1 (medium) defaults to the tail 60% — down to the full axis for the final stage's `_default_fit_bounds()`) and fits the slowest component *alone*. Each subsequent stage `k` fits ONLY the next-fastest component freely — always 2 free parameters, never more — with every previously-fixed (slower) component baked into the model as a constant (`_fixed_components_model()`); the final stage (the fastest component) is fit over the full range by default and finalizes the whole result. This avoids components trading off against each other the way an unconstrained joint fit easily can, since each slower component is already well-constrained by data where faster ones contribute essentially nothing. Initial guesses: the first stage reuses `_multiexp_initial_guess()` (same as N=1); every later stage's free component (`_free_component_initial_guess()`) is seeded from the residual after subtracting all fixed components, deliberately biased toward a shorter lifetime than the fastest one fixed so far (`min(window/10, tau_fastest_fixed/5)`) so it doesn't just converge onto an already-claimed timescale. All stages share the action bar/`DraggableSpan` machinery via `self._stage_idx` (0-based, `0..n_exp-1`; N=1 is immediately its own final stage) and a generic `_rank_name(rank, n_exp)` helper (`"slow"`/`"fast"` for N=2, `"slow"`/`"medium"`/`"fast"` for N=3) used throughout button text/status messages/save descriptions; canceling at any stage aborts the whole attempt (`_on_reset_fits()`), there's no "go back one stage" — each confirmed fixing stage is drawn immediately (dashed, colored per stage index via `_FIXED_STAGE_COLORS`: orange for slow, purple for medium) once locked in, even while a later stage is still being dragged. `FitParameters` is `(N,2)`, ordered fastest-first (row 0 = fastest, jointly fit in the final stage; later rows = progressively slower, each fixed from its own stage, in reverse fixing order). `FitCovarianceMatrix` is `(2N,2N)` but **block-diagonal**, not a true joint covariance — each stage's own 2×2 block on the diagonal, off-diagonal cross-blocks left at zero specifically because stages were never jointly optimized (documented in the dataset's own `description` attr so this isn't mistaken for "components are actually uncorrelated"). Separate `SlowRange` (N≥2) and `MediumRange` (N=3 only) datasets record each non-final stage's own range; `FitRange` is the final stage's (the range the fastest component, and the overall combined-curve overlay, spans).
  - **Changed 2026-08 (per-stage adjustability)**: each stage's dragged span used to freeze and stop being draggable the moment you moved on to the next stage — adjusting an earlier stage (e.g. the medium fit) meant restarting the whole multi-stage attempt from stage 0. Now every stage's span (`self._stage_progress`, one entry per stage `0..stage_idx`) stays live and movable for the whole in-progress attempt: the slow- and medium-decay spans can still be dragged while the fast/final span is being picked. Dragging any stage's span (`_on_stage_span_changed`) re-fits that stage and cascades forward through every later stage already added (`_recompute_from`), since each stage's model bakes in every earlier stage's fitted params as a fixed constant — an earlier stage's own fit never depends on a later one, so nothing needs to recompute backward. "Confirm"/"Add {next} fit" no longer freezes the current stage; it only appends the next stage's span on top, leaving all prior spans connected. Only the true final stage's "Confirm fit" (`_finalize_fit()`) locks everything in: freezes the current live state into `_fixed_stages`/`FitParameters` and tears down all the spans, same output schema as before. Canceling still aborts the whole attempt — there's no per-stage undo, only "start over" or "keep going forward".
  - This replaced an earlier 2026-08 design where N was "how many independent single-exponential fits" (each over its own separately-picked range, N ranges total, `FitRanges` (N×2)) and, before that, one where N meant "how many components summed into one *jointly*-optimized fit over one range" (no fixed-parameter staging at all) — `FitRanges`→`FitRange` (plural→singular) plus the iterative/fixed-parameter design are breaking schema changes each time; `visualizer.py`'s TRPL overlay was updated alongside the `FitRanges`→`FitRange` change (see below) and needed no further change for the iterative-fit generalization, since it only ever sums whatever `FitParameters` rows are present regardless of how they were obtained. Older saved files from any earlier schema lack `FitRange` and are simply skipped (no overlay).
  - **Added 2026-08 — baseline subtraction**: an optional "Baseline subtraction" group above the lifetime-fit group, sharing the same drag-a-`DraggableSpan`-then-Confirm UX and the same action bar (routed by `self._mode`, now `"idle"` | `"selecting"` | `"baseline_selecting"` — the two selection modes are mutually exclusive, each disabling the other's start button while active). Defaults the span to the tail 20% of the time axis (a TRPL decay's long-time tail is typically flat dark-count background). A constant is fit to the selected range — least-squares reduces to the mean `Counts` over the range — and, on Confirm, subtracted from every sample of a new `_counts_raw`/`_counts` split (`_counts_raw` is the pristine as-loaded array; `_counts` is what's actually plotted and fit, raw or baseline-subtracted). Applying or resetting the baseline invalidates any already-confirmed lifetime fit via `_invalidate_lifetime_fits()`, since it'd otherwise be stale relative to the changed `_counts`. If a baseline was applied, "Save" additionally writes the fitted constant as a scalar `Baseline` dataset (with the fit range as a `FitRange` attribute — note this is `Baseline`'s own attribute, distinct from the lifetime-fit's group-level `FitRange` dataset above) and the subtracted array as `CountsBased`, both in the same `analysis` subgroup — both are simply omitted if no baseline was ever applied.
- **`visualizer.py`** — "Visualizer": like `stitch.py`, one tab with a "File type" dropdown (`QStackedWidget` sidebar page + one shared canvas) — "Powerseries" and "TRPL" (added 2026-08; unrelated to `stitch.py`'s TRPL-conversion mode or the standalone `trpl.py` tab other than sharing HDF5 schemas). State/widgets namespaced `_ps_*`/`_trpl_*`, same convention as `stitch.py`.
  - **"Powerseries"**: load one or more HDF5 files into a shared list; two dropdowns — **Y data** (`SpectraDiff`, `Spectra_raw`, `PeakArea`, `PeakIntegral`, `Specsum`) and **X data** (`Wavelength`, `Energy`, `Power`, `Uncalibrated Power`, `Pump Fluence`) — pick what gets plotted. Each loaded file is checked for which of these actually exist (`_vis_ps_load_file()`'s `y_avail`/`x_avail` sets; nothing is synthesized — a missing dataset just isn't offered), and the two dropdowns mutually filter each other since every option belongs to exactly one of two mutually-exclusive modes: "spectra" (SpectraDiff/Spectra_raw × Wavelength/Energy) or "scalar" (PeakArea/PeakIntegral/Specsum × Power/Uncalibrated Power/Pump Fluence). Only the *passive* combo (the one not just changed) gets narrowed to the active one's compatible-and-available options — narrowing *both* on every change was tried first and created a dead end (once "scalar" narrowed the Y list, "SpectraDiff" was no longer offered anywhere to switch back with); the active combo always keeps its full list, so the round trip back to the other mode is always reachable through it. Spectra-mode legend labels show pump fluence if the file has it, else calibrated power, else uncalibrated power. "Inspect peaks…" replicates the Analysis tab's live "Inspect fits" view (see below) purely from a saved file — requires the `analysis` subgroup and specifically `FitWindowX`/`FitWindowRawY`/`BackgroundData`/`FitParameters` (a critical-path error if the subgroup or those datasets are missing, e.g. a file saved before the 2026-08 schema extension). "Show Data" (unchanged) opens a dialog listing every dataset/group/attribute in the selected file's HDF5 structure (via `io_utils._h5_contents_summary()`). The old "Legend quantity" radio group (power / power density / pump fluence) and "Plot integrated spectrum vs pump fluence" checkbox were removed 2026-08 — both are strictly subsumed by the new X/Y dropdowns plus the automatic legend rule.
  - **"TRPL"**: load one or more TRPL HDF5 files (via `io_utils._read_trpl_h5_file`) into their own list, overlaid on a log-y, downsampled canvas (same `setClipToView`/`setDownsampling`/`antialias=False` technique as `trpl.py`/`stitch.py`'s TRPL-conversion preview — smooth even at ~65k points/curve). A "Show fit intervals & functions" checkbox toggles, per file, an `analysis`-subgroup overlay (shaded `FitRange` + a `sum_i a_i·exp(-b_i·Times)` curve summed from every row of `FitParameters`, colored to match that file's curve) if present; a lifetime-values label lists each loaded file's `Lifetime` array as text (or "—" if the file has no saved fit). **Changed 2026-08** alongside `trpl.py`'s move to a single shared fit range for a sum of N exponentials: reads `FitRange` (singular, one range) instead of the old per-component `FitRanges` (N×2), and evaluates the new `a_i·exp(-b_i·Times)` parameterization instead of the old `exp(b)·exp(a·Times)` one — files saved under the previous schema lack `FitRange` and are simply skipped (no overlay, same as any file with no saved fit).
- **`analysis.py`** — "Analysis": peak-picking → fit-window selection → `fit_nw`/`integrate_spectra` (via `nw_analysis.py`) → threshold detection (drag-select ASE region, linear fit, threshold ± error) → L-L curve plot → save results into the HDF5's `analysis` group. A click-driven wizard/state machine (`self._ana_mode`). "Inspect fits" (added 2026-08, mode `"inspect"`): once `fit_nw` has run, pick a peak from the dropdown and click "Inspect…" to cycle per-power-step (◀/▶) through that peak's individual fits — each view overlays the full raw spectrum, the windowed raw data highlighted, the exact fit interval shaded (`DraggableSpan(..., movable=False)`, a static replay, not draggable), and the fitted Gaussian/Lorentzian curve (evaluated from `nw.fits[j][i].popt` via `nw_analysis._gauss_n_model`/`_lorentz_n_model`, with the interpolated local background from `nw.fit_data[j][i]` added back so it overlays the raw-counts curve rather than the background-subtracted one) — a QA tool for eyeballing convergence/tracking-drift per step rather than trusting the aggregate L-L curve. "✓ Close inspect" returns to the L-L curve. The save routine persists enough of this (`FitWindowX`/`FitWindowRawY`/`BackgroundData`/`FitParameters`, extended 2026-08 — previously only the background curve's *values* were saved, not its x-positions or the raw windowed y, which wasn't enough to reconstruct the overlay from the file alone) that the Visualizer tab's "Inspect peaks…" can replicate this exact view without a live fitting session.
  - **Fixed 2026-08 (found via user report of a "weird jump" in saved `PeakIntegral` between two adjacent power steps, even though the fit itself — visible in Inspect fits — was smooth there)**: `_ana_integrate()` (always called right after `fit_nw` inside `_ana_fit()`) used to independently re-track each peak's window via raw argmax (whichever pixel has the highest *raw* count each step, not the fitted peak position) with **no local background subtraction at all**, then unconditionally overwrite `fit_nw`'s own `nw.peak_integral` — which *is* fitted-peak-tracked and local-background-corrected, and had already gone through this session's extensive window-tracking hardening — with this cruder value. Raw-argmax tracking is far more easily thrown by noise or a competing nearby feature than a fitted position, so it could show a visibly jumpy trend on the L-L plot / in the saved `PeakIntegral` dataset even when the underlying fit was perfectly well-behaved (confirmed on the reported file: `fit_nw`'s own value went 2475→3205, smooth; the value that was actually getting saved went 31677→22304, a spurious ~30% drop). Fixed by no longer having `_ana_integrate()` touch `nw.peak_integral` at all — it now only computes `nw.specsum` (a deliberately separate, simpler comparison series shown alongside "peak N integral" on the L-L plot as "integrate @ center ±width", which still uses the same raw-argmax/no-background approach — that's a distinct, clearly-labeled curve, not a silent substitution, so left as-is rather than in scope for this fix).
  - **Corrected 2026-08 (immediate follow-up, once the user clarified the intended semantics of both quantities)**: the above fix's premise — that `fit_nw`'s own `peak_int[j,i] = trapz(Y_bg, X_bg)` was "the correct" `PeakIntegral` — was itself wrong. `PeakIntegral` is meant to be the complete sum of counts within the tracked fit window with **no background subtraction at all** (depending only on the window and the raw data, not on the fit or its background mode), and `specsum` is meant to be the sum of the **entire spectrum**, not any peak's window. Both had drifted from that: `fit_nw`'s `peak_int` was background-subtracted (`Y_bg`, not raw `Y_raw`), and `_ana_integrate()`'s `specsum` was windowed/peak-tracked (inherited from its now-removed raw-argmax loop) instead of whole-spectrum. Fixed both at the root: `nw_analysis.fit_nw` now sets `peak_int[j, i] = trapz(Y_raw, X)` — computed once per step from the window alone, before any background-mode branching, so it's structurally incapable of depending on the fit or background subtraction. `_ana_integrate()`'s `specsum` computation dropped the entire per-peak window-tracking loop (no longer needed — summing the whole spectrum doesn't depend on which peak is selected) in favor of one `trapz(spectra[:, i], wl)` per power step, appended as a single entry (previously one per peak, now genuinely peak-independent) with a `label` key (`_ana_plot_ll`'s specsum rendering now prefers `entry["label"]`, falling back to the old `"@ center ±width"` format only for entries that still carry those legacy keys). Verified: `PeakIntegral` is now smooth end-to-end on the reported file (21474→21861→22369→23193→23691 across the previously-jumpy steps), and `specsum` exactly matches an independent whole-spectrum `trapz` check and is correctly ~2.7x larger than any single peak's own window sum.
  - **Extended 2026-08**: the Inspect overlay now also draws the local background curve itself (a dashed yellow line, from `nw.fit_data[j][i]`'s already-stored background column — no new computation, just wasn't drawn before) plus dotted vertical markers at the two x-positions its reference points were averaged from (`nw.bg_ref_x[j][i]`, new in `nw_analysis.fit_nw`; `None` for background modes with no such two-point concept, e.g. `'none'`/`'constant'`). Persisted as a new `BackgroundRefX` (n_peaks × n_powers × 2) dataset in the save routine, read by the Visualizer's saved-file replica the same way as the rest of this overlay's data — optional/backward-compatible, since older saved files simply won't have it and the reference markers are skipped rather than erroring.
  - **Fixed 2026-08**: `_ana_save()` read `nw.fit_function` for the saved `FitFunction` attribute, but `nw_analysis.fit_nw()` actually sets `nw.fit_model` — the attribute name never matched, so every saved file's `FitFunction` was silently always the getattr default `"gaussian"` regardless of which fit function the user actually picked (gauss2, lorentz1, ...). Likewise `nw.background_type` was read but never set anywhere, so `FitBackground` was always its `"linear"` default too. Both are now real: `fit_nw()` sets `nw.background_type = subtract_fit_background` alongside its existing `nw.fit_model = fitfunction`, and `_ana_save()` reads the correct `fit_model` name. Caught while building the Visualizer's Inspect-peaks feature, which parses `FitFunction` (e.g. `"gauss2"` → 2 sub-Gaussians) to pick the right model function — with the bug, every file claimed `"gaussian"`, a string the `re.match(r"(gauss|lorentz)(\d+)", ...)` parse doesn't even match.
- **`spotsize.py`** — "Spotsize": load an Excel/text beam-scan file, select two spans on the derivative curve, Gaussian-fit the edge, compute the 95.4% width and beam diameter (Δx × sin(angle)).
- **`sem.py`** — "SEM": nanowire width/height/angle measurement from SEM TIFF images, a Python port of the "smarter SEM" MATLAB toolset (`\\nas.ads.mwn.de\tuze\wsi\e24\SQN\Researchers\Haubmann Benjamin\01_PhD\10_Scripts\smarter SEM`). Three modes: **Automated** (whole-image binarize → contour-trace → `cv2.minAreaRect` fit, with edge/size/tilt rejection rules and a per-image "skip IDs" list, port of `edgeDetect.m`), **Semi-automated** (click near a wire → auto-crop a physical-size window around it → detect the tallest accepted blob in the crop, falling back to a manual 2-click measurement if detection fails or the result is too short, port of `edgeDetect_semiauto.m`), and **Manual** (plain 2-click distance measurement tagged with a measurement-type label, port of `click_on_image.m`/`smarterSEM.m`). All three modes share one results table (exportable to CSV) and a live mean±std stats readout (replacing the separate `getValues.m`/`combined.m` post-processing scripts). Core image-processing logic lives in `sem_utils.py` (root, no PyQt imports); pixel scale is parsed by regex-scanning the TIFF's embedded ASCII metadata footer for `Pixel Size = <value> <unit>` (editable per-image if not found or wrong). Adds `opencv-python` and `Pillow` as dependencies.
- **`plot.py`** — "Plot": load one or more HDF5 spectrum files, preview each as PL Intensity (arb. units) vs. energy (one line per power step, colored dark→light by ascending pump fluence via matplotlib's `plasma` colormap, legend outside the axes titled "Pump Fluence (uJ/cm²)" with unit-less values converted from the file's mJ/cm² to µJ/cm² — falls back to power in mW, with its own "mW" suffix per entry and a "Power (no fluence in file)" title, if a file has no `Pump_fluence` dataset; `plot_utils._legend_ncols()` picks a legend column count from the figure height and entry count so a long single-column legend can't shrink `constrained_layout`'s axes to squeeze the plot), then "Save all as PNG" writes one `.png` per loaded file next to its source `.h5` (same basename). **Deliberate exception to the pyqtgraph-only rule below**: this tab embeds a real `matplotlib.figure.Figure` via `FigureCanvasQTAgg` instead of `PGCanvas`, because the saved image must be a literal matplotlib figure (WYSIWYG with the preview) — figure construction lives in `plot_utils.py` (root, no Qt/pyplot imports, uses the `Figure` OO API directly so `savefig` works for any format regardless of the attached interactive canvas).
- **`fit.py`** — "Fit": load one Powerseries HDF5 file (via `io_utils._read_h5_spectrum`) and plot its highest-power `SpectraDiff` vs. `Energy`; pick a fit function from a dropdown (`FIT_FUNCTIONS` registry — currently only "Gaussian", reusing `pl._gaussian`), drag a single `DraggableSpan` to select the fit region, click "Fit" to run `scipy.optimize.curve_fit` over that span. The fit curve is overlaid on the spectrum and a `QDialog` pops up showing each parameter's value ± standard error (from `sqrt(diag(pcov))`) plus R². Adding a new fit function later just means adding an entry to `FIT_FUNCTIONS` with a callable and its parameter labels.

## Shared modules
- **`io_utils.py`** — pure data I/O: `.origin`/HDF5 read-write, power-calibration parsing, HDF5 spectrum reading (`_read_h5_spectrum`, used by the Plot tab), HDF5 structure introspection (`_h5_contents_summary`, used by the Visualizer tab's "Show Data" dialog), TRPL `.dat` parsing/writing (`_parse_trpl_dat`, `_write_trpl_h5_file`, used by the Convert tab) and TRPL HDF5 reading (`_read_trpl_h5_file`, used by the TRPL tab), and the shared atBS/atSample transmission-factor fit (`_compute_power_transmission`, used by both `_write_h5_file` and `_write_trpl_h5_file`). No UI, no plotting.
- **`sem_utils.py`** — pure image-processing logic for the SEM tab: TIFF+scale reading, blob detection/rectangle-fit, crop, and 2-point measurement. No UI.
- **`plot_utils.py`** — pure matplotlib figure-construction logic for the Plot tab (`build_spectrum_figure`, `png_path_for`). No Qt imports; `io_utils._read_h5_spectrum()` supplies the data it plots.

Only center/width are seeded from history — amplitude always comes from the current window's own data (`find_peaks` prominence), since intensity changes by orders of magnitude across a power series and the previous amplitude isn't a valid scale guess there. Three-part fix in `_fit_gauss`/`_fit_lorentz`: (1) a width/FWHM floor of ~1.5 samples below which a component is numerically decoupled from the data; (2) "strongest component" is now ranked by integrated area (`a*c`), not raw amplitude, since amplitude alone trades off against width; (3) a previous component isn't trusted as a seed at all if its own fitted area was <2% of that fit's total (i.e. already degenerate) — reused for the *next* two fixes below too.
  - **Fixed 2026-08 (second layer of the same regression, found via user report on the very next `gauss3` fit)**: even with the above fix, a *trusted* previous component's amplitude **bound** (`hi = a0*1.5`) was still set from `proms[match[i]]` — the prominence of whichever `find_peaks` candidate happened to be nearest to that trusted position in *this* step's own data. Fixed by bounding amplitude at `max(a0, window's own max Y) * 1.5` instead of just `a0 * 1.5` (both `_fit_gauss` and `_fit_lorentz`) — never narrower than before, just no longer allowed to collapse below what the window's own signal scale could support.
  - **Fixed 2026-08 (third layer, found via user report on a different power step in the same file)**: with the bound fixed, a trusted component's *initial guess* was still `proms[match[i]]` — a non-convex least-squares landscape can trap a local optimizer near a bad *starting point* even with an unrestricted bound available. Traced to the actual root cause: `_find_peaks_sorted`'s smoothing (previously `len(X)//10`, e.g. 10 points for a ~100-point window) was heavy enough to erase a real but subtle shoulder feature as a detectable local maximum *entirely* — not just de-prioritize it — so there was no good candidate to seed from in the first place, from history or fresh. Fixed the smoothing cap down to `min(3, len(X)//30)` (verified empirically to still resolve the shoulder while suppressing single-sample noise) and, as defense-in-depth, made a trusted component's amplitude *seed* the previous step's own amplitude value rather than the matched candidate's prominence (adjacent power steps are close enough that amplitude is a reasonable warm start; the bound above still allows the fit to move away from it).
  - **Added 2026-08**: `'linear_peakwidth'` background mode (`_fit_with_peakwidth_background` / `_peakwidth_linear_background`), opt-in via the Analysis tab's Background dropdown (added last so `'linear'` stays the default). `'linear'` mode's two reference points are always the fixed window's edges, which is only a good proxy for "just outside the peak" when the window is wide relative to however broad the peak happens to be *at that specific power step* — if the peak broadens substantially while the window width stays fixed (tracking one peak across a whole power series), the edges can end up sampling the peak's own wings instead of flat baseline. `'linear_peakwidth'` instead places its two reference points at (leftmost/rightmost sub-peak's fitted center ∓/± an integer number of sigma each, expressed via each component's own FWHM). The two multipliers (default 3 each) are independent and user-adjustable — `fit_nw(peakwidth_sigma_lo=…, peakwidth_sigma_hi=…)`, `QSpinBox`es in the Analysis Settings dialog's "Fit peaks" group (integer-only, since only whole-sigma multiples make sense here) — for asymmetric peaks or when only one side tends to clip into the peak's wing. Needs a fit to know where "outside the peak" is, so it's a two-pass process per spectrum: pass 1 fits with plain edge-based `'linear'` background just to locate the peak(s), pass 2 recomputes the background from that and re-fits (seeded from pass 1) — falls back to the pass-1 result untouched if either pass fails to converge. Noticeably slower (~2x fit calls) for that reason, hence opt-in rather than default. `subtract_local_background` and `_peakwidth_linear_background` both also return the two reference-point x-positions used (`ref_x`), threaded through `_fit_with_peakwidth_background` and stored per (peak, power step) as `nw.bg_ref_x` — for `analysis.py`'s Inspect view to mark exactly where the background was anchored (see its entry above).

That has two problems for gauss2+/lorentz2+: which component is "strongest" can flip between adjacent power steps whenever their relative areas cross over, discontinuously dragging the anchor between two different components' positions; and it frequently doesn't match where a user's initial manual click landed on a *combined*, overlapping multi-peak visual feature (any one component's own center can sit several nm away from the visual center of the merged hump the user actually clicked on). ## Plotting architecture — `plotting/` package
Every tab except `plot.py` plots exclusively through PyQtGraph via the shared `plotting/` package (migrated off Matplotlib in 2026-07). Each such tab imports only from `plotting` (never a submodule directly). `plot.py` is the one deliberate exception — see its entry above — and embeds matplotlib directly via `FigureCanvasQTAgg`, not `PGCanvas`. Note `matplotlib` came back as a `requirements.txt` dependency in 2026-07 when `nw_analysis.py` was moved into this repo — originally needed only for that module's own (unused-from-this-app) interactive functions and `pl.py`'s, `plot.py`'s embedded preview is the first tab to actually render matplotlib on-screen.

- **`canvas.py`** — `PGCanvas(pg.GraphicsLayoutWidget)`: the shared embeddable canvas. `reset_axes()` clears curves/ROIs/legend/colorbar and returns a fresh `plot_item` (full clear-and-rebuild on every redraw, matching every tab's existing redraw pattern — no incremental updates). `sigDataClicked(x, y, button)` replaces matplotlib's `button_press_event` for click-driven picking (used by `analysis.py`). `draw_idle()` is a no-op kept only so old call sites didn't need touching.
- **`theme.py`** — `apply_pg_theme()` (call once at startup, before any `PGCanvas`), `TAB10` palette, `PLASMA` colormap — matched to the app's dark `qt_material` theme.
- **`multiline.py`** — `MultiLinePlotter` + `LineColorScheme` strategy classes (`CategoricalScheme` = tab10-by-index, `SequentialScheme` = plasma-by-value, `LogAlphaRamp` = log-scaled opacity wrapper) — covers every "color N lines by file or by power" pattern across `stitch.py`/`visualizer.py`/`analysis.py`.
- **`colorbar.py`** — `GradientLegend(pg.ColorBarItem)`: a standalone plasma gradient legend (not attached to an image), used wherever lines are colored by power.
- **`regions.py`** — `DraggableSpan` (wraps `pg.LinearRegionItem`; one class serves both the interactive picker role and the "replay a stored span" role via `set_range()`) and `DraggableRect` (wraps `pg.RectROI`; a persistent resizable box — deliberately different UX from matplotlib's click-drag `RectangleSelector`, confirmed acceptable). Both track their own add/remove lifecycle since `reset_axes()` wipes them on every redraw.
- **`scatter.py`** — `RecolorableScatter`: thin wrapper over `pg.ScatterPlotItem` for per-point recoloring (analysis.py's threshold-region highlighting).
- **`annotations.py`** — `FilledRegion` (`pg.FillBetweenItem` wrapper) and `MeasurementArrow` (hand-built double-headed arrow + label composite — no built-in PyQtGraph equivalent; spotsize.py's only consumer).
- **`toolbar.py`** — `make_pg_toolbar(canvas)`: a minimal 2-button toolbar (Export Image…, Reset View) replacing matplotlib's `NavigationToolbar2QT`. Pan/zoom is handled by PyQtGraph's built-in mouse interactions (scroll-zoom, drag-pan, right-drag box-zoom) instead of dedicated buttons.

**Known pyqtgraph gotcha (worked around in `canvas.py`)**: toggling `setLogMode` right after `reset_axes()` can hit a `10**range` overflow if the ViewBox still holds a stale large linear range from whatever was plotted before the clear. `reset_axes()` explicitly resets the view to a small known range before re-enabling auto-range to avoid this.

**Known pyqtgraph gotcha — large curves are slow with the app-wide antialias default**: `theme.py`'s `apply_pg_theme()` sets `antialias=True` globally, which combined with a non-default pen width forces pyqtgraph's slow per-segment rendering path; without downsampling, every pan/zoom also repaints every point. Fine for the few-thousand-point curves most tabs plot, but heavily laggy for large ones (`stitch.py`'s TRPL-conversion mode's ~65536-point TRPL histograms, `trpl.py`'s, `xrd.py`'s large scans). Fix, applied at each such call site: `ax.setClipToView(True)`, `ax.setDownsampling(auto=True, mode="peak")`, and `MultiLinePlotter.plot(..., width=1.0, antialias=False)` — the `antialias` kwarg on `MultiLinePlotter.plot()` (added for this) defaults to `None`, inheriting the global setting, so every other call site is unaffected.

`PGCanvas.set_welcome(msg)` (added 2026-08 for `stitch.py`'s merged tab, also used by `visualizer.py`'s) updates and re-shows the welcome/placeholder screen — for a canvas shared across multiple modes (a "File type" switch) where each mode wants its own placeholder text instead of the one fixed at `__init__`.

**Known pyqtgraph limitation**: `pg.LegendItem` only renders items with an `.opts` attribute (`PlotDataItem`-like) — `LinearRegionItem`/`InfiniteLine` cannot be added via `legend.addItem(...)`. Span regions are identified by on-canvas color + sidebar labels instead of a legend entry; axvline-style markers use `InfiniteLine`'s own `label=`/`labelOpts=` instead.
